# PulseWork · 企业通用 AI 工作助手

![PulseWork 产品预览](./public/og.png)

**[体验在线 Demo](https://pulsework-ai-portfolio.zoe00010.chatgpt.site/)**

PulseWork 是我为企业通用办公场景设计的 AI 工作助手。它不只回答“制度里怎么写”，还会结合用户的地区、职级和权限判断哪条规则适用，并在获得确认后调用企业系统完成任务。

这个项目不是为了再做一个聊天窗口。我想验证的是：当 AI 从“提供信息”走向“完成工作”时，产品应该怎样处理企业上下文、执行权限、人工确认和效果评测。

## 我从什么问题出发

员工完成一笔报销，表面上是填一张单据，实际上通常要经历四步：

1. 找到制度，并确认是最新版本；
2. 根据地区、职级和差旅类型判断是否适用；
3. 切换到费用系统，重复录入发票和行程信息；
4. 提交后再去审批系统跟进状态。

问题不是“没有系统”，而是知识、判断和行动被分散在不同入口。因此，PulseWork 的产品目标不是提高聊天轮数，而是提高**有效任务完成率**，同时降低查找、判断和系统切换的成本。

## 为什么先做这三个场景

我用“使用频率、跨系统复杂度、结果可验证性”做了 MVP 取舍，最后保留三类任务：

| 场景 | 用户真正要完成的事 | 我重点验证的产品能力 |
| --- | --- | --- |
| 制度查询 | 得到适用于自己的结论，而不是一段通用摘要 | 权限感知检索、版本校验、段落级引用 |
| 差旅报销 | 确认是否符合标准，并完成提交 | 票据解析、制度匹配、工具调用、写操作确认 |
| 新人入职 | 知道谁在什么时间完成什么 | 任务拆解、依赖编排、跨 HR、IT 与行政协同 |

这三个场景分别覆盖了“回答”、“回答后执行”和“多角色协同”，可以用较小的范围验证企业 Agent 的主要边界。

## 产品怎么工作

```text
用户目标
   ↓
意图与风险识别
   ↓
权限感知的企业知识检索 → 重排 / 版本校验 / 引用
   ↓
Agent 生成执行计划
   ↓
只读操作自动执行 → 写操作等待用户确认 → 高风险操作拒绝
   ↓
结果、来源、执行记录与失败恢复
```

我特意把“回答”和“行动”分开。读制度、查状态可以自动进行；创建报销单、分派入职任务等写操作必须告知影响范围，等用户确认后再执行。付款、删除和权限变更不在 MVP 的自主执行范围内。

## Demo 里可以体验什么

- **工作助手**：报销、入职和制度查询拥有独立的 Agent Trace 和结果页。
- **任务中心**：展示运行中、待确认和异常任务，让用户只在需要介入时介入。
- **知识空间**：展示数据源同步、检索可用性和过期文档风险。
- **Agent 市集**：用场景化卡片表达能力边界，而不是让用户先理解模型或工作流。
- **案例拆解**：用滚动吸附和鼠标微交互讲清问题、方案和产品决策。
- **评测中心**：把正确性、引用可信度、工具选择、任务完成和安全性放在同一版本视图中。

首页的灵宠“牧牧”是一个小型交互实验。它最初使用位图逐帧动画，但在迭代中出现了轮廓跳变和图层割裂。最终改为浏览器合成层驱动，只让鼻口与下颌进行微幅运动，同时保留低动态模式。这次迭代也提醒我：“帧数更高”不等于“体感更流畅”，先找准感知问题比叠参数更重要。

## 我怎么评估它

对于企业 AI 产品，“回答看起来不错”不是可回归的标准。我将评测拆成五个维度：

| 维度 | 核心问题 |
| --- | --- |
| Correctness | 结论是否符合制度与用户上下文 |
| Groundedness | 结论是否能被有效文档和原文段落支持 |
| Tool selection | Agent 是否在正确时机选择正确工具 |
| Task completion | 用户目标是否真正完成，失败后是否可恢复 |
| Safety | 是否发生越权检索、提示注入绕过或未确认写操作 |

评测集覆盖正向、边界和对抗三类样本。例如：查询差旅标准、处理缺失日期的发票、请求查看他人薪资，以及要求 Agent 跳过确认直接提交高额报销。样例见 [`evals/dataset.json`](./evals/dataset.json)。

Demo 中展示的指标用于表达评测方法，不代表已在真实企业环境中上线运行。如果进入灰度阶段，我会先开放只读问答，再开放沙箱写操作，并将低分会话脱敏后回流到回归评测集。

## 这个项目做了哪些取舍

- **先覆盖通用任务，不先做自定义 Agent 搭建器。** 对普通员工来说，“把事做完”比“学会编排工作流”更重要。
- **先展示执行记录，再追求完全无感。** 在用户建立信任前，看到 Agent 找了什么、判断了什么、将要做什么，比省掉几秒更重要。
- **默认限制写操作，不用自动化程度证明 Agent 能力。** 企业产品的可控性不是附加项，而是进入真实流程的前提。
- **把评测当成产品流程，而不是发布前的一次验收。** 每个失败样本都应该能回流、标注和回归。

## 项目状态

当前为可交互高保真原型，用于验证产品架构、关键交互和评测方法；未连接真实企业数据或生产系统。

产品定义、业务场景、交互方案、评测设计与文档由我独立完成。产品结构参考了 Dify 的应用编排、RAGFlow 的检索可观测性，以及 Langfuse 的数据集与评测工作流。
